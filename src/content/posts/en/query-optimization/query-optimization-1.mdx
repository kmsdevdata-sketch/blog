## Choosing the APIs to analyze
First, I needed to select the APIs to test and improve, so I looked for candidates using the criteria below.
- Identify the main APIs that read from the database.
- → Classify candidates by read frequency, query complexity, and the possibility of data growth.
- → Select two or three target APIs from those candidates.
Wihada handles buyer, seller, and administrator APIs in the same application. For the initial classification, I focused on the seller APIs because I thought they would manage relatively more data.

I used Codex to identify and classify the APIs, and the list below was the result.

| Area | APIs |
|---|---|
| Dashboard aggregates | `GET /seller/dashboard`, `GET /seller/dashboard/revenue`, `GET /seller/dashboard/revenue/transactions` |
| Order list and calendar | `GET /seller/orders`, `GET /seller/orders/calendar/today`, `GET /seller/orders/calendar/week`, `GET /seller/orders/calendar/month` |
| Inquiry and chat lists | `GET /seller/inquiries`, `GET /seller/inquiries/{inquiryId}/events` |
| Inquiry history | `GET /seller/inquiries/{inquiryId}/order-form-submissions`, `GET /seller/inquiries/{inquiryId}/confirmations` |
| Overall store status | `GET /seller/store/management-status` |
| Various settings and notice management | `GET /seller/store/settings`, `PUT /seller/store/settings`, `GET /seller/notices`, `PUT /seller/notices` |
| Image and gallery lists | `GET /seller/gallery-items`, `GET /seller/representative-images` |

At this point, I excluded single-item APIs and first narrowed the list to items, such as list and aggregate APIs, whose query costs could rise as the number of records retrieved increased.

As for read frequency, there was no real user data, so I could only guess. I therefore removed it from the selection criteria and chose items based on code whose cost would grow with the data and where repeated reads occurred.

1. `GET /seller/inquiries`: loads all inquiries for a store and separately queries the number of unread items for each inquiry.
2. `GET /seller/dashboard`: queries several aggregates and the number of unread items for each inquiry.
3. `GET /seller/orders`: loads the entire accumulated order list.

## Measuring the baseline
### Test tool
I used k6 as the test tool. The biggest reason I chose k6 was that I had used it before, and I came to use it often because the process from installation to writing the code and running it was simpler than with other tools.

### Test scenario
#### Goal
The goal of this test was to get baseline values for how long each API takes with the current data and how that changes as the number of requests increases, rather than to find out "the maximum number of users who can connect" or "how much load it can withstand." (I would optimize the queries, measure again, and compare the results.)
#### Request rate
| Stage | Request rate | Duration | Purpose |
| --- | ------ | ------ | ------------ |
| Warm-up | Low | 30–60 seconds | Reduce first-run effects |
| Stage 1 | 1 request/second | 2 minutes | Baseline response time |
| Stage 2 | 3 requests/second | 2 minutes | Effect of increased traffic |
| Stage 3 | 5 requests/second | 2 minutes | Effect of another increase |
> Reason for warming up: the first few requests can be affected by the JVM's running state, database connection preparation, and disk caching, so warming up lets me distinguish those effects when measuring.
#### Expected results and metrics
| Metric | What I wanted to check |
| -------------------------------- | ---------------------------- |
| SQL executions per request | Does an inquiry or dashboard request repeat a query for every inquiry? |
| Execution time per SQL and total database time | Which queries consume the most time? |
| API response time, p50 and p95 | How much does database work affect the actual response time? |
| Returned item count and response size | Am I comparing responses with the same amount of data? |
| Error rate | Do requests fail as the system slows down? |
| Actual request count and dropped_iterations | Did the planned traffic actually reach the application? |
### Test code
```javascript
import http from 'k6/http';
import { check } from 'k6';

// APIs under test
const paths = {
    inquiries: '/seller/inquiries',
    dashboard: '/seller/dashboard',
    orders: '/seller/orders',
};

// Values supplied at runtime
const target = __ENV.TARGET;
const rate = Number(__ENV.RATE);
const minItems = Number(__ENV.MIN_ITEMS || 1000);
const baseUrl = __ENV.BASE_URL || 'http://localhost:8080';
const token = __ENV.SELLER_TOKEN || 'local-seller-token';

export const options = {
    scenarios: {
        seller_query: {
            executor: 'constant-arrival-rate',
            rate,
            timeUnit: '1s',
            duration: __ENV.DURATION || '2m',
            preAllocatedVUs: 20,
            maxVUs: 100,
        },
    },
    thresholds: {
        checks: ['rate==1'],
    },
};

export default function () {
    const response = http.get(`${baseUrl}${paths[target]}`, {
        headers: {
            Authorization: `Bearer ${token}`,
        },
    });

    let body = null;
    if (response.status === 200) {
        try {
            body = response.json();
        } catch (_) {
            // A non-JSON response fails the validation below
        }
    }

    const validData =
        body !== null &&
        body.success === true &&
        (target === 'dashboard'
            ? body.data !== null &&
            typeof body.data === 'object' &&
            !Array.isArray(body.data)
            : Array.isArray(body.data) && body.data.length >= minItems);

    check(response, {
        'HTTP 200': (r) => r.status === 200,
        'expected response data': () => validData,
    });
}
```

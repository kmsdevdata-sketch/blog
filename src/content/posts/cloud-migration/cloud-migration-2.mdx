## 동기화 감시

동기화 감시 ? 구독 생성 단계는 명령을 실행하자마자 거의 바로 끝나게 되고 실제 데이터 복사는 postgreSQL 안에서 따로 돌게된다.  
그래서 플랫폼은 "구독은 만들었는데 데이터가 언제 다 넘어온건지" 알수 없는데 그걸 확인하기 위해서 지속적으로 상태를 확인해야하는데 => 이게 동기화 감시이다.

+ 동기화 감시를 하는 추가적인 이유는 해당 뒷단계들이 모두 **"대상이 원본을 다 따라잡았다"** 라는 가정하게 진행이 되기때문이다.

- 섀도 리허설: 데이터가 덜 넘어온 상태에서 응답 비교를 하면 당연히 불일치
- DB 전환 : 남은 변경이 많으면 쓰기를 멈춘 채 기다려야 하는 시간이 길어진다 => 다운타임이 길어진다.

### 동기화감시는 무엇을 확인할까

#### 대상 DB : 테이블 별 상태

| Status | Meaning |
|---|---|
| `i` | Initializing |
| `d` | Data copy in progress |
| `f` | Data copy completed |
| `s` | Synchronized, handing off to the apply worker |
| `r` | Ready, receiving real-time changes only |

#### 원본 DB : lag

원본이 지금까지 쓴 WAL위치(LSN- 1편 후반부 참고),슬롯이 "여기까지 받았다"라고 확인한 위치의 차이를 바이트로 계산한다.

그리고 위에 두값을 바탕으로 단계를 파악한다 `copy → catchup → streaming`

- 하나라도 i/d/f면 copy
- 복사는 끝났지만 s가 남았거나 lag가 1MiB를 넘거나 lag를 모르면 catchup
- 전부 r이고 lag ≤ 1MiB면 streaming

## 섀도 리허설

섀도 리허설의 목적은 DB 전환 전에 대상에서도 앱이 똑같이 응답하는지 실제 트래픽을 보내보는것이다.

```sql
-- Original DB
SELECT name FROM users WHERE id = 1;
-- Result: kim

-- Target DB
SELECT name FROM users WHERE id = 1;
-- Result: lee
```

기존에는 체크섬 기반으로 행수 비교를 하였지만 내부 데이터 정합성까지는 보장할수 없다고 판단하여 추가하게 되었다.

### 복사 방식

중계 Envoy 라우트에 "GET이면서 허용 경로"조건으로 미러링 정책을 붙인다.  
사용자 요청은 원래대로 원본으로 가고 복사본만 비교 수집기로 간다.  
쓰기는 절대 복사하지 않는다 => 대상 DB에 쓰기가 들어가면 복제 데이터 꼬임 우려

---

## PgBouncer 설치 완료 대기 -> 앱 연결 변경

현재 앞선 단계에서 이미 PgBouncer 설치를 시작해 두었기 때문에 설치가 끝났는지만 대기한다.  
PgBouncer 설치가 완료되면 현재 앱이 아직 원본 DB에 붙어있기 때문에 해당 단계에서 앱이 바라보는 주소를 PgBouncer 로 바꾸어준다.

```text
바꾸기 전:  앱 ──────────────→ 원본 DB
바꾼 후:    앱 ──→ PgBouncer ──→ 원본 DB
```

1. PgBouncer 설치 완료되었는지 확인
2. 앱의 새 DB주소 만들기 : 앱이 쓰던 DB주소에서 목적지만 PgBouncer로 바꾼다
3. 앱이 PgBouncer로 나갈수 있게 열어주기 : 만약 방화벽 규칙때문에 PgBouncer로 가는길이 없다면 해당 통로만 열어준다
4. PgBouncer 주소로 실제 접속 가능한지 확인 : DNS가 늦게 열릴 염려가 있기에 정확히 연결성공이 뜬뒤에 넘어간다
5. 앱 설정 바꾸고 재시작 : 옛주소를 쓰는 앱이 하나도 안남을때 까지 기다리기

## 감시와 전환 승인 요청

앱까지 PgBouncer로 연결되면 이제 전환 승인을 받기 전까지 계속 감시하며 대기한다.  
5초마다 아래 두 가지를 확인한다.

1. 복제 상태 : 여전히 `streaming`인지, lag는 얼마나 되는지
2. 지금 쓰기를 멈춰도 되는 순간인지
   - 오래 걸리는 트랜잭션이 돌고 있는지 => 쓰기를 멈추면 이 트랜잭션이 끝날 때까지 기다려야 한다
   - 락을 기다리는 쿼리가 있는지
   - 복제가 꺼져 있거나 밀려 있는지

원본이 쓰기를 담당하고 있고 복제가 `streaming`이면 웹의 두 번째 승인 화면에 **전환 계획**을 보낸다  
전환 계획에는 지금 복제 상태와 위 점검 결과가 담겨 있어서 사용자가 보고 승인 여부를 판단할 수 있다.

- 매 주기마다 보내지 않고 상태가 바뀔 때만 다시 보낸다.
- 처음 시도, 거부 후 재시도, 롤백 후 재시도처럼 새로운 시도가 생길 때마다 승인 요청도 함께 보낸다.

섀도 리허설을 했다면 그 결과도 전환 계획에 한 줄로 들어간다.

| 항목 | 상태 | 값 | 근거 |
|---|---|---|---|
| shadow | pass | 1238/1240 | 일치율 0.99 이상 · 대상 5xx 0건 |

> 섀도 결과는 **표시만** 한다. warn이 나와도 승인을 막지 않고 최종 판단은 사람이 한다.

웹에서 승인 버튼을 누르면 Workflow에 전환 신호가 전달되고 => 여기서부터 실제 DB 전환이 시작된다.

## 마무리

이번 데이터 이전 과정에서 사전 점검과 섀도 트래픽 부분은 내가 구현했지만, 실제 데이터를 옮기는 복제와 전환 흐름은 팀원분이 맡았던 부분이라 이번에 코드를 하나하나 따라가 보면서 많이 배울 수 있었다.

특히 인상 깊었던 부분은 PgBouncer를 활용한 전환 방식이다.  
앱을 DB에 직접 붙여두면 DB를 바꿀 때마다 앱을 재시작해야 하는데, 앱과 DB 사이에 PgBouncer를 미리 끼워두고 재시작은 처음 한 번만 한 뒤, 실제 전환은 아주 짧게 쓰기를 멈추고 목적지만 바꾸는 방식으로 다운타임을 줄였다.

또 쓰기를 멈추기 전에 "지금 멈춰도 되는 순간인지"를 먼저 확인하는 부분도 좋았다.  
오래 걸리는 트랜잭션이나 락을 기다리는 쿼리가 있는 상태에서 쓰기를 멈추면 그만큼 대기 시간이 길어지기 때문에, 단순히 복제가 따라잡았는지만 보는 게 아니라 DB가 실제로 어떤 상태인지까지 고려해야 한다는 걸 알게 되었다.

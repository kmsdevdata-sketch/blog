## 계획수립

SQL 및 실행계획을 분석하는 과정은 아래 두가지 질문에 답하는 과정이라 볼수있다.

1. **API 요청 한 번에 어떤 SQL이 몇 번 실행되는가** 
2. **그 중 시간이 드는 SQL은 DB가 어떤 방식으로 실행하는가**

### 첫번째 질문 답하기 : SQL 로그 확인

선수지식 : [Spring Boot 로깅 공식 문서](https://docs.spring.io/spring-boot/reference/features/logging.html) 를 확인하여(`Log Groups`,`Log Level` 섹션 확인) SQL을 로그에 표시하는 방법을 확인할 수 있다.
예를 들어 문의 API 로그가 대략 아래와 같이 나온다면

```
문의 목록 조회 SQL                         1회
특정 문의의 읽지 않은 항목 수 조회 SQL       1,000회 반복
```

**"문의 1,000건을 처리하기 위해 개별 조회 SQL이 반복되는구나!"** 를 알수있다.
SQL의 종류 혹은 실행 횟수를 파악하기 위한것으로 `왜 호출되었는지` , `반복 횟수를 줄일 수 있는지` 판단할수 있다.

### 두번째 질문 답하기 : 실행계획으로 개별 SQL 분석

선수지식 : [PostgreSQL의 EXPLAIN 문서](https://www.postgresql.org/docs/17/using-explain.html) 를 확인하여 `EXPLAIN`,`EXPLAIN ANALYZE` 에 대해서 파악할수 있다.

> 실행계획 : PostgreSQL이 SQL을 처리하기 위해 선택한 작업순서.
> ex.테이블을 처음부터 흟을지,인덱스를 사용할지,여러 테이블을 어떻게 결합할지 등

1번에서 발견한 SQL 중 분석할 대상을 골라 해당 SQL 한 번이 왜 오래 걸리는지 확인한다.

## SQL 분석

우선 SQL 로그 설정을 아래와 같이 설정해준다.

```yaml
logging:  
  level:  
    sql: debug
```

위와 같이 설정하면 기본 `sql`로그 그룹을 `DEBUG`로 설정하므로 Hibernate SQL로그도 표시된다.

상세하게 정리하여 보면 4개의 구간으로 나눌수 있다.

1. 요청 준비 구간 : 사용자 조회 3회,판매자 온보딩 조회 1회,소유 스토어 조회 1회 = 5회
2. 목록 본체 : 토큰으로 확인된 판매자의 스토어에 속한 문의 목록 조회 1회
3. 목록에 표시할 정보 : 스토어 1회,구매자 일괄 조회 1회,최근 채팅 항목·메시지·주문서 조회 각 1회 = 5회
4. 읽지 않은 항목 수 : 문의 하나마다 `count`SQL 실행 **1,002회**

문제가 3가지나 보인다. 어떤 분들은 상태를 보고 폭소를 하셨을지 모르겠다😂

1. 같은 판매자 조회를 3회 실행함 : 승인 필터,스토어 필터,컨트롤러 인자 처리에서 각각 사용자를 찾는 듯함. 중복 조회 가능성 
2. 같은 스토어를 2회 조회함 : 요청 준비 때 , 문의 목록을 만들 때 
3. 1,002회 반복조회 

하지만 이는 종류와 실행 횟수만 파악한 것이므로 성능 영향순위를 파악할 근거는 충분치 않다.
거기에 현재 눈에 밟히는 점들은 모두 어플리케이션의 호출 흐름에서 발생하는 것으로 판단되지만 사실 조회자체가 적더라도 해당 한번이 300ms가 걸릴 수도 있는것이기에 3개 모두 실행계획을 분석해보자 

## 실행 계획 분석

### 1. 판매자 조회

```sql
-- 1. 판매자 조회

EXPLAIN (ANALYZE, BUFFERS)
SELECT u.id, u.cognito_sub, u.created_at, u.email, u.name,
	   u.payer_id, u.phone_number, u.profile_asset_id, u.role,
	   u.signup_provider, u.status, u.updated_at
FROM users u
WHERE u.cognito_sub = '<seller-cognito-sub>';
```

각 항목의 의미는 아래와 같다.

|항목|의미|
|---|---|
|`Index Scan using uk_users_cognito_sub`|`cognito_sub` 인덱스로 사용자를 찾음|
|`rows=1`|예상과 실제 모두 1명 조회|
|`actual time=0.233..0.234`|인덱스 탐색부터 결과를 얻기까지 약 0.234ms|

|`Buffers: shared hit=3`|필요한 DB 페이지 3개가 메모리 캐시에 있었음|
|`Planning Time: 0.648 ms`|실행계획을 세우는 데 걸린 시간|

### 3. 문의별 읽지 않은 항목 수

```sql
-- 3. 문의별 읽지 않은 항목 수: API 요청에서 이 SQL이 1,002회 실행됨
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(cti.id)
FROM chat_timeline_items cti
WHERE cti.inquiry_id = '021c3458-157f-4811-e605-965441d90cba'
  AND cti.sender_user_id <> 'c822ed91-47a1-452f-90fe-ab92c64f3dbb'
  AND cti.created_at > TIMESTAMPTZ '2026-09-26 07:08:16.070986+00';
```
![문의별 읽지 않은 항목 수 실행계획 결과 ](assets/query-plan-4.png)

각 항목의 의미는 아래와 같다.

| 항목                                                                 | 의미                                             |
| ------------------------------------------------------------------ | ---------------------------------------------- |
| `Aggregate ... (actual time=0.664..0.665 rows=1 loops=1)`          | 조건에 맞는 항목을 세어 `count` 결과 **1행**을 만듦            |
| `Buffers: shared hit=12`                                           | 이 단계 전체에서 접근한 DB 페이지가 메모리 캐시에 있었음              |
| `Bitmap Heap Scan ... (actual time=0.284..0.649 rows=5 loops=1)`   | 인덱스가 찾은 위치를 따라 실제 테이블 데이터를 읽어 **5건**을 남김       |
| `Recheck Cond: ...`                                                | `inquiry_id`와 `created_at` 조건을 테이블 데이터에서도 확인   |
| `Filter: sender_user_id <> ...`                                    | 판매자가 보낸 항목을 제외                                 |
| `Rows Removed by Filter: 5`                                        | 위 필터에서 **5건 제외**                               |
| `Heap Blocks: exact=10`                                            | 실제 테이블 페이지 **10개**에 접근                         |
| `Buffers: shared hit=12`                                           | 이 단계의 페이지 접근 수. 위 `Aggregate`의 12와 **합산하지 않음** |
| `Bitmap Index Scan ... (actual time=0.134..0.135 rows=10 loops=1)` | 인덱스에서 조건에 맞는 **후보 10건**을 찾음                    |
| `Index Cond: ...`                                                  | 인덱스 검색에 사용한 조건: 문의 ID와 읽은 시각 이후                |
| `Buffers: shared hit=2`                                            | 인덱스 검색 과정에서 접근한 캐시 페이지. 위 12에 포함됨              |
| `Planning Time: 0.571 ms`                                          | 실행계획을 세운 시간                                    |
| `Execution Time: 0.858 ms`                                         | **이 SQL 한 번**을 실행한 전체 시간                       |

### 실행계획 전체 정리

| 조회                      | 실행계획의 핵심                                | DB 실행 시간 |
| ----------------------- | --------------------------------------- | -------- |
| 판매자 조회                  | `cognito_sub` 인덱스로 1건 조회, 캐시 페이지 3개 접근  | 0.330ms  |
| 스토어 조회: `owner_user_id` | 테이블 전체 탐색으로 1건 조회, 캐시 페이지 1개 접근         | 0.217ms  |
| 스토어 조회: `id`            | 테이블 전체 탐색으로 1건 조회, 캐시 페이지 1개 접근         | 0.204ms  |
| 읽지 않은 항목 수              | 인덱스로 후보 10건 탐색 → 발신자 조건으로 5건 제외 → 5건 집계 | 0.858ms  |

이전에 측정한 문의 API 응답 시간은 약 `400ms`였다. 이때 1번부터 3번까지는 DB 실행 시간을 절반으로 줄인다 하여도 API 응답 시간 개선에는 큰 영향을 주지 못하기 때문에 해당 SQL들의 실행 속도를 개선하는 작업은 우선순위가 낮다고 판단하였다. (물론 중복 호출은 별도로 평가할 필요가 있다.)
다만 4번의 경우 실제로는 1,002회가 호출되므로 누적 비용까지 추가적으로 측정이 필요하다고 판단하였다.

### 읽지 않은 항목 수 - 별도 누적 비용 측정

`pg-stat-statements` 를 활용하여 1,002회 조회의 총 실행 시간을 측정한다.

> `pg-stat-statements` 는 PostgreSQL의 실행 통계 확장 기능으로써 SQL별 호출 횟수,누적 DB실행 시간을 기록하여 줍니다.

**1. API 호출 전의 SQL 실행 통계를 임시 저장**

```sql

CREATE TEMP TABLE unread_before AS
SELECT userid, dbid, queryid, calls, total_exec_time
FROM pg_stat_statements
WHERE dbid = (
	SELECT oid FROM pg_database WHERE datname = current_database()
);
```

**2. Postman 활용하여 API 호출결과 응답시간 : 454 ms**

**3. API 호출 후 통계에서 호출 전 통계를 빼서,읽지 않은 항목 수 조회가 그사이 몇 번 실행되었고 DB에서 총 몇 ms걸렸는지 계산**

```sql
SELECT
    s.query,
    s.calls - COALESCE(b.calls, 0) AS calls_during_request,
    ROUND(
        (s.total_exec_time - COALESCE(b.total_exec_time, 0))::numeric,
        3
    ) AS total_db_execution_ms,
    ROUND(
        (
            (s.total_exec_time - COALESCE(b.total_exec_time, 0))
            / NULLIF(s.calls - COALESCE(b.calls, 0), 0)
        )::numeric,
        4
    ) AS mean_db_execution_ms
FROM pg_stat_statements s
LEFT JOIN unread_before b
  ON b.userid = s.userid
 AND b.dbid = s.dbid
 AND b.queryid = s.queryid
WHERE s.dbid = (
    SELECT oid FROM pg_database WHERE datname = current_database()
)
  AND s.query ILIKE '%count(%'
  AND s.query ILIKE '%chat_timeline_items%'
  AND s.query ILIKE '%sender_user_id%'
  AND s.query ILIKE '%created_at%'
ORDER BY calls_during_request DESC;
```
